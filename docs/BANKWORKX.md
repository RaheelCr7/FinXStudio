# BankWorkx: a second bank app on the same platform

BankWorkx is a money-management app (balance, spending, budgets, cards) built on the same journey engine as Meezan Digital. Its look follows the fintech design kit you supplied: a lavender canvas, a blue gradient balance card, cyan highlights, a mint action button, rounded cards, charts, and a bottom tab bar.

It shows that one codebase can carry several banks: the journeys, engine and Studio are shared, and each bank brings its own look, name, ids and sandbox customers.

## Run it

```bash
# 1. Studio (a second terminal), then load the BankWorkx journeys into it
cd apps/studio && pnpm dev
cd apps/studio && npx tsx scripts/seed-journey.ts all        # add-money, add-card, connect-account, create-budget

# 2. The app in a browser
pnpm bankworkx:web

# 3. Or on the iPhone Simulator / an Android emulator
pnpm ios:sim --brand bankworkx --install
pnpm android:apk --brand bankworkx --install
```

Without Studio the app falls back to the journeys bundled inside it, so the demo still works offline.

## Checked on

The web build, and the iOS Simulator (iPhone 17 Pro, iOS 26.5): sign-in, dashboard with the chart, the action sheet, a full *Add money* journey with a balance update, and dark mode. All four journeys ran on iOS (typed card number, hidden password, switches, tiles). The first BankWorkx iOS build took 1 min 27 s and rebuilds about 50 s. On an Android 14 emulator the app starts in under half a second and the dashboard renders fully (the 21.8 MB APK is `bankworkx-0.1.0-1-uat-arm64.apk`); on 2 November 2026 the Invest screens also ran there: the portfolio, a stock page, the watchlist star, and a *Sell investment* sale ($50 of a holding, with the position updating). The other journeys were not re-run on Android. A real iPhone has not been tried. To open BankWorkx on the emulator: `FINX_BRAND=bankworkx node apps/bank-app/scripts/android-emulator.mjs launch`.

**Between my accounts: how it differs from the prototype spec.** It is built from the blocks FinX has, so the countdown on the rate, the live conversion summary under the amount, the "Today that is 1 USD = ..." line on the first screen, the note in Activity and the launch values (`accountId`, `toId`, `amount`) are not there; the review says the rate is held for 30 seconds. A rate that ran out is found when the code is entered (nothing is moved) rather than on the confirm button, because only the conversion call checks it. Errors are separate screens (`problem`, `amountProblem`, `failed`) chosen from the bank's error code. The bank's options `allowFx` and `fxFee` are plain data (`opt.allowFx`, `opt.fxFee`, on unless set to false). In the sandbox, BankWorkx quotes with no margin and the spec's Euro and Dirham rates (the reference bank keeps its 0.5% spread), a renewed quote moves by fixed steps within 0.04% so tests repeat, and `bank.transfers.own` is the same-currency move (`CURRENCY_MISMATCH` if the currencies differ). Its scenarios use sandbox conditions (`timeout`, `unavailable`, `latencyMs`, `frozen`, `transferFails`) and the `advance` step that moves the clock; they and the mutation check are in `packages/finx-mcp/src/scenarios.test.ts`.

Edit: the same fields filled in; a change of nickname or label alone is saved with no check and no code. Delete: asks no code; a payee used by a scheduled payment is refused unless *Also cancel these scheduled payments* is on |

**Add, edit or delete a payee: how it differs from the prototype spec.** Launch values now exist but this journey was built without them, so it still always starts by asking what to do; AC-9 (return to the transfer the payee was added from) and the *Send money* and *Back to the payment* buttons are not built, nor is *Fill with a sample payee*. The blocks are `select` chips and tiles, a `menu` for the payee list (the chip is in its second line) and `consent` for the ticks; the bank's errors come back as one message shown on the screen, the first problem found (the prototype lists all). Errors are chosen from the bank's code (`route`), and *Try again* goes back to where the person was (`retry`). The bank's options `nameCheck`, `allowCancelSchedules` and `labels` are plain data (`opt.*`, on unless set to false). A change of the name or the account asks for a code and repeats the name check, but only a change of the bank details makes the payee new for 24 hours again (the shared rule; the journey text of the spec says the name does too). The wrong-code lock uses the engine's `otpVerify` counter, so `STEP_UP_FAILED` is not a bank code here (`OTP_REQUIRED` is). In the sandbox: `bank.payees.validate`, `check`, `save`, `update` and `delete`; `bank.beneficiaries.list` keeps its shape and adds the payee details, `coolingOffUntil` and `allowanceLeft`; `bank.transfers.create` holds a payee added in the last 24 hours to 500.00 USD in total (`BENEFICIARY_COOLING_OFF`), counted per payee. The name check registry is a small table of fake owners (Camille Dubois, Lena Fischer, James Whitfield, Omar Haddad, Priya Raman, Faisal Al-Harbi, Rania Haddad); an account it does not know, and anything abroad, cannot be checked. **Send money: how it differs from the prototype spec.** The engine has no live redraw while typing and no per-field messages from the bank, so: the journey starts at the type unless it is opened with one (`launch.type`, see *Launch values and opening one journey from another*); an alias is a thin entry that opens it with the type set; the speed cards come on their own step after the amount, because the bank can only say which speeds fit once it has the amount (the first that fits is chosen, one over its limit is marked and refused); the bank's refusals (balance, limits, the 500.00 of a new payee, the purpose) are one screen with the bank's own words and the button to fix it, not a message under the field; the payee's address is asked on its own step when the bank says the rule applies; and the format checks of the payee fields are patterns on the fields while the bank checks the rest (check digits, the country of an IBAN or a BIC) and shows its message on the screen. The engine says "Enter an amount" for a zero amount and "Enter a whole amount, without decimals" for a currency without decimals; the "Reference" pattern has one message for characters and length. "Between my accounts" is its own journey (`own-transfer`); only the first home market (routing number and account; Standard, Same day and Instant) is configured, so the name check (Markets B to D) and the other markets' fields are not built; the bank's `allowFx` and `nameCheck` options and the mobile alias of Market D go with them. The Payments hub, tracker, notifications and `single-transfer` (Quick transfer) are not built. A held payment changes neither the balance nor the daily limit (acceptance criterion AC-12 of the spec; its scenario T-19 says the balance drops). The bank's options are plain data (`opt.*`, on unless set to false; Priority and *who pays the charges* are off unless set to true): `typeInternal`, `typeDomestic`, `typeIntl`, `speedStandard`, `speedSameDay`, `speedInstant`, `speedPriority`, `chargeChoice`, `allowLater`, `coolingOff`. In the sandbox: `bank.payees.lookup`, `bank.payments.quote`, `bank.payments.create` and `bank.schedules.list`; `bank.accounts.list` takes `homeOnly` (only the accounts that can pay someone else) and `bank.beneficiaries.list` takes `sendType`; `bank.payees.validate` takes `strict` (the country rules of a payment abroad: IBAN of the country, transit number, IFSC, BSB, 18-digit Mexican account, the country letters of the BIC) and returns `key`, `currency` and `country`. The rails are data (`packages/mock-bank-api/src/payments.ts`): Standard (free, 1 to 2 business days, up to 25,000.00), Same day (1.00, today), Instant (0.25, in seconds, up to 500,000.00), abroad 25.00 (+15.00 when the sender pays all charges, Priority 40.00), a BankWorkx customer free and instant up to 25,000.00. A payment in another currency is priced at the mid-market rate with no margin and the price holds for 60 seconds (the BankWorkx sandbox has the rates of the spec for its 12 currencies). The scenario conditions gain `limitUsed` (money already sent today) and `unavailable: ["rail:rtp"]` takes one speed down. The new-payee allowance (500.00 USD in 24 hours) now also covers a payee typed in the payment and not saved; what was sent counts when it is saved. The proof is in `packages/finx-mcp/src/scenarios.test.ts`.

A bill part-paid shows what is left next time; one paid in full says *Already paid* |

**Pay a bill: how it differs from the prototype spec.** The Meezan journey `pay-a-bill` is a different journey (slug, look and billers) and is not changed; this one is `pay-bill`, for BankWorkx only. The engine has no launch values, no live redraw while typing and no per-field messages from the bank, so: the journey always starts at the directory (the saved-biller row and *Repeat payment* open it, not a screen further on); the directory is filtered with a **Search** button (name, category chips) rather than as the person types; the bill is looked up when **Continue** is pressed on the reference screen, not as soon as the reference is valid, and what it found (amount due, due date, *Overdue*) is on the amount screen, while "No bill found", "Already paid", "No bill due" and "Biller unavailable" are a screen of their own with the spec's button (Edit, Back, Try again); an empty reference says "Required" (the engine's message) rather than "Enter the reference."; the minimum and other amount are left out, not dimmed, when `allowPartial` is off (with "This bill can only be paid in full."); the live summary under the amount (fee, rate, *You pay*) is on the review, and the biller's fee is named on the amount screen; the sheet that asks for the code is a screen (`otp`, "Pay bill"). Errors are screens chosen from the bank's code (`refProblem`, `amountProblem`, `failed`, `timeout`, `slow`, `unavailable`); the wrong-code lock is the shared `locked` screen (the engine counts `otpVerify` failures), so `STEP_UP_FAILED` is not a bank code and its words are only on `failed` (a payment sent without a verified code). The currency of the bill ($) is fixed in the journey, as in the prototype. The balance, the daily limit (tested on the amount plus the fee, in the currency of the account) and the new amount due are the bank's. The bank's options are plain data (`opt.*`, on unless set to false): `billFetch`, `allowPartial`, `allowCrossCurrency`, `offerSaveBiller`, `offerAutopay`. *Pay automatically* is made by the payment itself (`bank.bills.pay` with `autopay`): the monthly entry is added to the list that `bank.schedules.list` reads, a month after the due date on a business day, up to 1.5 times the amount due rounded up to 10. The journey `schedule-payment` that changes or cancels it, the notification, the `limits` call and the Payments hub (*View in Payments* leaves the journey) are not built. In the sandbox: `bank.billers.list` (takes `category` and `q`), `bank.bills.saved` (lists, or saves with `billerId` and `reference`), `bank.bills.lookup`, `bank.bills.quote` (prices and checks before the review) and `bank.bills.pay`; a BankWorkx customer gets the bank's own directory of 16 billers (`packages/mock-bank-api/src/bills.ts`), the Meezan customers keep their four. The last four digits of the reference choose the outcome (1111 biller unavailable, 0000 no bill, 9999 or paid in full already paid, 5555 no bill due, 7777 overdue with a 5% late fee and a due date 9 days ago, 3333 the amount due rises by 12.00 once, on the review; anything else (1000 + number mod 9000) / 20 due in (number mod 20) + 3 days), and the payment shows in Activity under the biller's name, category *Bills*. The proof is in `packages/finx-mcp/src/scenarios.test.ts`.

**Mobile top-up: how it differs from the prototype spec.** The Meezan top-up (carriers Jazz, Zong, Telenor and Ufone, PKR 50 to 5,000) is a different thing and is not changed; a BankWorkx customer gets the operators and fixed amounts of `topup.ts`, behind the same `bank.carriers.list` and `bank.topup.create`. The engine has no "Checking the number…" wait, no per-field messages from the bank and no message for an empty choice, so: the deep link that skips the operator step is the launch value `launch.operatorId` (acceptance criterion AC-9: a valid operator goes straight to the number, an unknown one is ignored, and it is used once, so *Top up again* asks again; **Change** is always shown); an empty number says "Required" (the engine's message); the operator, the amount and the saved number are one tap on a row, so nothing can be left empty; the number, the day's allowance and the balance are checked by the bank (`bank.topup.check`) when **Continue** is pressed on the account step, not on the review button, so a refused number, limit or balance is a screen with the bank's message and the button to fix it (*Change number*, *Try again*, *Change amount*, *Change account*) before the review, and "Not enough in this account." needs no rule of its own in the journey (the bank checks the balance again at payment); a slow answer to the check is the `slow` screen ("Nothing was taken", Try again), because no money moves, and only a slow top-up says "Check Activity"; the timeout screen is an error result (the result block has no warning tone); the wrong-code message is a toast "That code isn’t right. Try again." (the spec's shared rule also has "{n} tries left", which the engine's code field does not show); the name of a saved number says "Use 2 to 20 characters." for both a short and a long name; the amount screen is `bank.topup.amounts` (an operator's amounts) rather than `bank.carriers.list` with a parameter, so that a scenario can make it fail on its own. **Schedule a payment and Cancel a standing order: how they differ from the prototype spec.** These were built before launch values and `toJourney` existed, so they are not changed here (the deep links and the alias in cancel mode can now be built). The engine has no live redraw while typing, no per-field messages from the bank and no way to dim a card, so: both journeys start at what the person can do or at the list of what is scheduled (the spec's deep links with `payeeId`, `savedBillId`, `scheduleId` and `mode` are not built, nor are the Payments and Home entry points); `cancel-standing-order` is a journey of its own instead of an alias of `schedule-payment` in cancel mode (so AC-7 and its scenario T-8 of the spec are proved there, with 6 criteria of its own), and *Schedule a payment* after a cancellation is *Back to scheduled*; the kind, the payee, the bill and the quick choices are one tap on a row, so "Choose what to schedule." and "Choose who to pay." cannot happen; the card "Different currency" is a message after **Continue** ("Choose two accounts in the same currency."), as is "Choose two different accounts."; an empty date or number says "Required" (the engine's message); the date is the calendar field, which the engine only checks for being a real date (it cannot offer the next 365 weekdays or know today's date from the sandbox clock), and the rest of the date rules ("Choose a date from tomorrow.", "Choose a weekday.", "Choose a date within the next 12 months.") are the bank's, shown on a screen with **Change date** when the person leaves the date; the number of payments uses a pattern per frequency ("Enter a number from 2 to 104."); the daily limit is not read into the amount field (the `limits` call is not made) but checked by the bank when the date is left ("That is over your daily limit."); the code sheet is a screen (`otp`, "Schedule payment" or "Save changes"); the wrong-code lock is the shared `locked` screen, so `STEP_UP_FAILED` is not a bank code. ### Launch values and opening one journey from another

**Launch values.** A journey can be opened with values at data paths that are there *before* its entry screen runs, so the entry (its `onEnter`, a branch screen, `navigation.rules`) can branch on them. Apps: `app.openJourney(slug, initial, launch)`; players: the `launch` prop (renderer-core: `launch` option of `JourneyRunner` and `JourneyController`). Existing `initial` answers are unchanged: they are still filled in *after* the first screen opens. Without launch values nothing changes. By convention the journey reads them at `launch.*` (for example `launch.type`, `launch.operatorId`), copies what it wants into its own data on the entry screen and, where it should be used once, clears it (Mobile top-up). Scenarios take a `launch` object (and the simulator a `launch` option).

**Opening another journey.** `{ "type": "navigate", "toJourney": "personal-transfer", "with": { "launch.type": "international", "pt.note": "{{t.note}}" } }`. The values are read from the calling journey's data at that moment (a `with` value that is a whole `{{template}}` keeps its type) and passed as the other journey's launch values; the bank's options (`opt.*`) go along, because they belong to the bank. A navigation rule of the screen that matches wins over `toJourney`, as it does over `to`. The runner raises the request (`openJourney` option, `onOpenJourney` on the controller and the players); the app opens the target by slug the way `openJourney` does, including a copy made for the bank (`personal-transfer-acme`): `BankApp.openChained` in the apps, a route change in the web app. A target that cannot be loaded closes the calling journey with the notice "That journey is not available right now." In the Studio preview, where only the journey being edited is loaded, nothing opens: the screen says "This step opens another journey, which is not loaded here." and the person stays.

**`returnTo`.** Not built, and it does nothing: the calling journey is *replaced* by the target, and nothing comes back to it when the target ends (the person goes back to the app). It stays in the schema, reserved, so that a journey that sets it keeps working. It needs the calling journey's state to be kept and restored; that is the follow-up.

**Lint.** `with` values are checked like other templates (an unknown data path is a lint issue). A `toJourney` that is not a journey of the catalog or of BankWorkx or CAB is a *warning* (the advice of `finx_lint_journey` / `finx_save_journey_draft`, code `unknown_journey`), not a blocking issue, since a bank may add its own journeys. The expression `get(map, key)` reads an entry whose key is data (for example the operator the journey was launched with in `ctx.carriers`).

**Where it is used.** *To a BankWorkx customer* and *Abroad* open Send money with `launch.type` (their 20 screens are no longer copied; their scenarios follow the chain in the simulator, `expectOpens` asserts what was opened, so every rule is proved where it lives; Send money gained AC-14 for being opened with a type). *Mobile top-up* takes `launch.operatorId`. The simulator follows a chain to journeys it is given (`journeys`, default: the BankWorkx journeys) and otherwise records "opens journey X with values Y".

They carry `apps: ["bankworkx"]`, so the Meezan app never shows them. A journey with no `apps` belongs to Meezan.

## Signing in and security (step 6b, part 1)

BankWorkx has a real sign-in: a username and a password, a one-time code on a new or unusual device, a new password when the old one expired, trusting the device, and quick sign-in. Part 1 is the sandbox's credential model and five journeys; the shell screens and the Security journeys are part 2 (see the end). Spec: the "Signing in and security" group of the journey catalog. This is lean and country-neutral: no country rules were invented.

### How the apps sign in

On the web (`apps/bank-web`, `components/Login.tsx`) and the phone (`apps/bank-app/src/bankworkx/SignIn.tsx`) the sign-in screen is the `sign-in` journey. **The journey signs the customer in at the sandbox bank, and the app then asks the bank who is signed in.** Nothing else passes between them:

1. `BankApp` (packages/bank-client) starts with a bank that nobody is signed in to (`new MockBank("signed-out")`). Only the sign-in and recovery adapters answer; anything else is `NOT_SIGNED_IN`.
2. The journey calls `bank.auth.signIn` (the password, checked as a hash), then, when the bank asks, the one-time code, a new password, `trustDevice` and `setQuickSignIn`, and last `bank.auth.completeSignIn`. That opens the session: **the same bank object now serves the customer who signed in** (so the journey's adapter handle stays valid), with the same session as the sandbox customer of the same name (Alex has Personal, Alpha as Maker, Beta as Approver).
3. The journey ends. `app.finishSignIn()` reads `bank.signedIn` and `bank.persona.id` and opens that customer. It returns false unless the bank was the one made for the sign-in and a customer is signed in, so a journey that was closed, or a customer chosen another way (a restored tab), cannot sign anyone in without a password.
4. **No secret travels.** The journey clears the password, the new password, the PIN and the code as soon as the bank has them (also when the bank did not answer: the `problem` screen clears them again); the bank never answers with a password, hash, PIN or the code; the events of a run carry only screen names, field names and error codes; the tab remembers a customer id and the language, never a password. All of it is tested (`packages/finx-mcp/src/signin-security.test.ts`, `packages/bank-client/src/signin.test.ts`, `apps/bank-web/components/pages.test.tsx`).
5. What the bank remembers (`AccessDirectory`: users, trusted devices, locks, the remembered username) is held by the app for as long as it runs, so signing out and in again finds the device trusted and the username greeted. A reload starts the sandbox empty, as everywhere in the sandbox.

**The customer picker stays, for development.** On the web a small link under the sign-in ("Use the sandbox customer picker") or `?picker=1` shows the list of sandbox customers (Alex Morgan, Sam Rivera) and "Log in" as before; "Back to sign in" returns. On the phone the same link sits under the sign-in. A bank without a real sign-in (Meezan, the other brands, and a project of the BankWorkx look that has no `sign-in` journey) is unchanged: the picker is its sign-in. `ProjectInfo.signIn` (web) and `BankAppDeps.signIn` turn it on; the web app turns it on for projects of the BankWorkx look, the phone app for BankWorkx.

### Where it differs from the spec (the prototype), and why

- **Outcomes are data, not errors**, as in the Cairo Amman Bank sandbox (`{ ok: false, code, attemptsLeft }`), so a journey can show how many tries are left; the engine puts only the code and the message of a thrown error where a journey can read them. Codes that are thrown (the code, the token, the service) are routed by `ctx.error.code`.
- **5 wrong passwords lock**, as the journey says (the shell text says 3). One constant, `ACCESS.maxFailedSignIns`. Wrong quick PINs share that count and also turn quick sign-in off after 3.
- **000000 is wrong and 999999 expired** in the sign-in and recovery (the prototype); for a signed-in customer's own code the sandbox keeps accepting 000000, as before. A resend gives the next code (482101 ...), so "the old code is useless" is real.
- The sample profiles of the prototype (mobile 5550104410, born 1 Jan 1990) are replaced by the seed table's (mobile +1 415 555 0142, born 14 March 1988).
- The date of birth is one calendar field (`dateInput`); the prototype has Day, Month and Year. "Changed" shows `03 / 11 / 2026` (the `date` formatter), not "Tue 3 Nov 2026". The "photo ID check" in the unlock card is not there: unlocking is the code. "Contact us" and "Call us instead" show a sandbox number, there is no `contact-support` journey.
- The engine lacks, and these were **skipped, not built**: the live checklist beyond the length (the other four rules are checked by the bank and reported with their message), Show / Hide beside the password (the field has its own Show button), the Caps Lock line, the resend countdown (the resend is a button; a scenario cannot press the code field's own resend), the "Register" link (no such journey), the place and time on the device card, the bank's options as app settings (the apps do not pass `opt.*`), and a separate returning-sign-in pop-up (the "Welcome back" card and the PIN field do it).
- Not built in part 1 and built or listed in part 2 (see the section below): the shell screens (Session timeout, the Step-up dialog, Sign-out confirmation, System states, Settings > Security), `bank.system.status`, the biometric prompt of the phone, the notifications the spec raises, and the journeys `setup-quick-login`, `change-password`, `trusted-devices` and `change-quick-pin`.
- The AI catalog (`finx_get_catalog`) grew with 13 of the adapters above (the rest are in this document); it is trimmed to one line each and its cap raised from 90,000 to 95,000 (and `MAX_OUTPUT_CHARS` with it, because the whole catalog has to arrive as valid JSON). Part 2 added the 8 Security adapters the journeys call (about 2,000 characters, one line each, plus 420 saved by shortening older entries): the catalog is 96,090 and the cap and `MAX_OUTPUT_CHARS` are 96,500 (+1,500). Later the adapters became an index in `finx_get_catalog` (one line each, by family, with the inputs, results and errors fetched by `adapter`), so the whole catalog is about 53,200 and its cap is 56,000 (`CATALOG_MAX_CHARS`); a new adapter adds about 80 characters to the catalog and its full entry only to the adapter it describes. `MAX_OUTPUT_CHARS` of the other tools is back to 90,000.

- Set up quick sign-in: the three PIN rules of Change quick PIN it only opens (`pinLockOff`, `currentPin`, `pinSame`), and the error path of *turning off*, which a scenario cannot fail on its own (it would have to turn a method on first, with the same adapter down).

What each one does, and the numbers:

- **Change password.** The current password (the bank checks it, shares the sign-in count: attempts left 4, 3, 2, 1, the fifth locks the profile and offers *Reset password* and *Contact support*), the new password twice (checked by the bank against the same five rules as the sign-in plus "not the one you have", each with its own message; the checklist shows the length live and the other four after Continue, because the engine cannot ask the bank on every key press), then a one-time code (three tries; the third ends the attempt; an expired code asks to go back). The result shows the date and whether other devices were signed out (`opt.signOutOthers`, on unless a bank sets it off; the sandbox has no per-device sessions, so it only reports the choice).
- **Trusted devices.** A view: each device with its last use ("This device · Last used Now", "Yesterday, 18:20", "12 Oct 2026"), "{n} of 5" (`opt.limit`), a tap on another device opens "Remove {device}?" with a code field, and *Sign out other devices* (`opt.signOutAll`, only when there is another device). Three wrong codes lock the view ("Too many wrong codes. Try again later.") until the person leaves and comes back. The device in hand is never removed (the bank refuses it too). "Device removed" is a green line on the list, not a transient toast: the engine drops a toast when a journey changes screen.
- **Set up quick sign-in.** The device and what is on now; Face ID or fingerprint, passkey, a 6-digit PIN or *Turn off*, each only when the bank offers it (`opt.allowBio`, `allowPasskey`, `allowPin`) and, for Face ID, only when the device can (the bank's record of the device: a flag `biometricAvailable`). The PIN is checked by the bank before the code is asked for (`bank.devices.checkPin`, which changes nothing). Turning on needs a code; turning off does not, and the device returns to the password. One method per device: turning another on replaces the PIN. From the result with a PIN on, *Change PIN* opens Change quick PIN.
- **Change quick PIN.** The current PIN is the proof (no code): wrong ones answer "{n} tries left", the third turns quick sign-in off ("Quick PIN turned off", *Set up again*). A new 6-digit PIN that is not the current one, a repeat, a run or part of the phone number, entered twice. With no PIN the screen is "No quick PIN yet" with *Set up quick sign-in*.

**Biometrics are state, not a prompt.** A browser or the sandbox cannot show a fingerprint or face prompt. The bank records per device whether it can (`biometricAvailable`; Alex's iPhone and tablet can, his Work laptop cannot, and a scenario can be run on that laptop with `conditions.device: "browser"`), and "Confirm on this device" stands in for the phone's own prompt, which cannot fail here (the spec plans `BIO_FAILED`; not built). On the web there is no biometrics row at all, as the spec says; on the phone it is a switch that is disabled, with the spec's helper text, when the device cannot.

### Secrets: how the journeys keep none

- The bank keeps *that* the current password or PIN was checked (for five minutes, once), not the secret: `bank.password.check` and `bank.devices.verifyPin` leave the proof, and `bank.password.change` / `bank.devices.changePin` use it when they are not given the current one. The journeys clear the current password and PIN as soon as the bank has checked them.
- The new password is held only from its screen to the call that saves it, and is cleared on every way out (a failure, the third wrong code, an expired code, Back, the step-up having run out). The new PIN is held from the first screen to the code (Set up) or to the answer (Change). Tests walk each way out and look at the run's answers, the transcript and the events (`packages/finx-mcp/src/security-journeys.test.ts`); the bank's record of the customer, its answers and the dump of both hold no password, no PIN, no hash and no code.
- The sandbox keeps hashes only; no answer carries a secret; no value is in a URL (the address carries launch values by their declared names, never a secret), a log or an analytics event.

### What the sandbox adds

- **A step-up before a change** (`stepUpGate`): `bank.password.check` / `change`, `bank.devices.remove` / `changePin`, `bank.devices.setQuickSignIn` (turning on) and `bank.device.setDefault` (to biometrics) answer `STEP_UP_REQUIRED` unless the customer stepped up in the last five minutes. Reading, turning something off (it only makes sign-in stricter) and `checkPin` need none. Only for a customer who has a session (Alex): the others have no step-up to give.
- **A strict one-time code for a customer's own changes**: `bank.otp.send` / `verify` with `strict: true` (a flag the journeys send): 000000 is wrong, 999999 is expired, a code works for 5 minutes and once, `resend: true` asks again (at most 3 more) and the old code becomes useless, the third wrong code answers `OTP_LOCKED` and even the right code is refused until a new one is asked for. Without `strict` the persona's code keeps working as it always has (000000 is accepted): other journeys are untouched.
- **Outcomes as data** where a journey shows the tries left: `bank.password.check` answers `{ ok: false, code: "INVALID_PASSWORD", attemptsLeft }` (or `ACCOUNT_LOCKED`), `bank.devices.verifyPin` `{ ok: false, code: "PIN_WRONG", triesLeft }` (or `PIN_LOCKED`). Part 1 threw them; its unit tests were changed to say so.
- **The step-up takes a quick PIN** (`method: "pin"`) as well as the password and the device's own check; a wrong password or PIN counts with the sign-in's five tries ("That password isn't right. 4 tries left."), and the last one locks the profile and ends the session (`LOCKED`).
- `bank.devices.list` with `scope`, the count, `others` and `lastUsedText`; `bank.devices.checkPin`; `bank.loginHistory.list` with `order: "oldest"`; `passwordChangedAt` in `bank.device.options` for the signed-in customer; `bank.password.policy` says `PASSWORD_SAME` to a signed-in customer who types the password they have; the scenario device `browser` (above).
- Ten new rules a mutation can switch off: `stepUpGate`, `changeNeedsCode`, `currentPassword`, `passwordSame`, `removeNeedsCode`, `currentDeviceKept`, `quickNeedsCode`, `pinLockOff`, `currentPin`, `pinSame`.

### The shell

- **Settings > Security** (`/personal/more/settings/security`; phone: More > Settings > Security): the password row ("Last changed 2 May 2026"), Sign in with (Biometrics switch on the phone, Quick PIN "Set up" or "Change", Default sign in "Change"), Trusted devices "3 of 5", and the login history. The history has the six columns of the spec, chips (Signed in, Wrong password, Locked, New device code, Signed out for inactivity), filters for the result, the period (7, 30, 90 days) and the device, "Clear filters", the oldest-first sort on the Date header, 20 rows a page, a details sheet with *Change password* and, when the journey exists, *This wasn't me*, the loading, empty ("Your sign-ins will appear here.", "No sign-ins to show for these filters.") and error states. Cards on phones. Its buttons are launch points marked `stepUp` (Change password, Trusted devices, Change quick PIN, Quick sign-in, Biometrics): a button shows only when the place holds `security.manage`, the app has the journey and the bank has not switched it off.
- **Step-up**: before a journey whose launch point is marked `stepUp`, the app asks (title "Confirm it's you", what it is for, then the password, or the quick PIN when that is how this device signs in, then the code); it is not asked again for five minutes. A journey opened by its address asks too ("Confirm it's you first", Back). The bank refuses the change without it whatever a screen shows.
- **Session timeout** (`packages/bank-client/src/idle.ts`, in `BankApp`): five quiet minutes (no tap, key press, scroll or request) sign the person out; from the 240th second "Still there?" with the seconds left, *Stay signed in* (calls `bank.session.keepAlive` and starts the clock again) and *Sign out now*. A tap does not end the warning; a request made behind it does not either. The sandbox bank ends the session at the same time (`conditions.idleTimeoutSeconds`), so a call after a sleep answers `SESSION_EXPIRED`. A phone that was in the background for more than five minutes comes back signed out with no warning. The sign-in then says "You were signed out for your security. Sign in again to continue. Nothing you were doing was saved." and returns to where the customer was: on the web the address (`?next=`, never into a journey), on the phone the tab (`keepPlace`), only for the same customer. Off unless the app asks (both BankWorkx apps do). `NEXT_PUBLIC_FINX_IDLE_SECONDS` shortens it for a demo (a build setting, not an address).
- **Sign-out**: "Sign out?" / "You'll need to sign in again." asks once (the timeout and the lock do not); the app calls `bank.auth.signOut` (and signs out all the same if the bank cannot be told), clears the session, the place, the step-up, every cached screen, the journey and its drafts, sheets, search and filters, toasts, and on the web `sessionStorage`; it keeps the language, light or dark, the device and the greeting.
- **Returning sign-in**: a remembered device greets the person ("Welcome back, Alex") and offers *Use PIN* (or *Use Face ID* on a phone where it is on), as part 1 built it inside the sign-in journey; after a timeout it also says why.
- **System states** that were cheap: the backend-unavailable and timeout panels ("This service is not available right now" / "This is taking longer than expected", "Nothing was changed.", *Try again*) on the tabs and on Security, the signed-out notice, and on the web the offline banner ("You're offline. We'll reconnect when you are." then "You're back online" for 3 seconds).

### Not built, and why

- **`bank.system.status`, maintenance and forced update**, **offline lists with "Last updated" and disabled send buttons**, and the phone's connection state: the sandbox has no status service and the apps no connection API in this build.
- **A returning-sign-in pop-up over the form** (PIN keypad or "Unlock") and the phone's real biometric prompt: the "Welcome back" card and the PIN field do it, and a prompt cannot run in a browser or the sandbox.
- **Sign-in counts as a step-up for 300 seconds**: not built; the first sensitive action after a sign-in asks (safer, and the combined demo's step-up tests stay as they were).
- **Settings > Security for a customer with one place** (Sam Rivera): the classic shell has no More > Security; the sandbox only gives a step-up to a customer with a session.
- **The "This wasn't me" button** opens `new-message` (topic Fraud or security) since step 7, slice D; before it the details sheet said to call the bank. **Rename a device** (the spec removed it; the adapter exists). **The login history's date-range picker** (a Period list instead), and notifications raised by a change (the spec plans them). **Signing out of other devices on a password change** only reports the choice.
- The phone screens are type-checked only: no emulator was run for part 2.

### Money safety, as built

- **A code before anything sensitive.** The bank (not the screen) refuses without a fresh one-time code: a PIN (`card-pin`), a virtual card, a replacement order (always: see below), unfreezing, and any change that loosens a card (a higher limit, a control turned on, a trip). Tightening (freeze, a lower limit, a control off, alerts), blocking a lost or stolen card and reporting a payment ask for none, because they only make the card harder to use or move no money.
- **Nothing sensitive is kept.** The sandbox keeps the last four digits and the expiry of a card, a hash of a PIN, and nothing else: a virtual card's full number and security code are made once, handed to the one call that asked and shown once on the result (the journey clears them when the person leaves; a test looks in the run's data and in the bank's dump); the number and security code of a card being saved are held from the first screen to the last call and cleared on every way out. A PIN, a code and a security code are secure fields that no transcript or event carries.
- **Money in whole units.** Limits and fees are compared in minor units (`toMinor`, `roundMoney`); an amount with more decimals than the currency has is refused (`LIMIT_INVALID`).
- **A failure path for every bank call**, with the words of the spec ("Nothing was changed.", "Nothing was sent.", "Nothing was saved."), and a slow answer never says the action happened.
- `bank.cards.replace` is in `MOVES_MONEY` (lint): the journey needs the tick, the code before the order and a way out of the call.

### Money safety, privacy and security, as built

- **A code before a contact detail changes.** The bank (not the screen) refuses a change of mobile number, email or address without the one-time code of the signed-in customer (`OTP_REQUIRED`); the code goes to the number on file, never to the new one, is spent by the call that used it, and a refused change spends none. Three wrong codes end the attempt (`OTP_LOCKED`), 999999 is expired. A new mobile number needs a code of its own, sent to the new number (`bank.profile.sendContactCode` and `verifyContact`, three tries), or the bank refuses with `CONTACT_NOT_VERIFIED`. After a mobile change the next code goes to the new number, and sign-in and recovery use it too.
- **The old and the new contact are told.** A mobile change texts the old and the new number, an email change emails the old and the new address (a change that waits asks the new one to confirm), an address change texts the number on file. The notices go to a masked destination and say what happened without a value; the log of a change says what was done (`profile.mobile.updated`), never the value; scenarios read both with `sandbox.more.inspect`. A note ("Mobile number updated", "Maple Credit Union connected") is added to the notification list, without the value.
- **No personal data in logs or answers.** The contact screen of the journey (`bank.profile.contacts`) answers masked values only (`•••• 0142`, `a•••@example.com`) and the address the person sees on the screen; the result holds the masked value; the journey clears the typed value and the codes once the bank has them; tests look at the run's data, the outbox and the log for the number, the email and the address.
- **What the person writes is data.** A message, a reply, a subject, a request's details and a file name are stored as written and drawn as text by every block that shows them (no block of these journeys renders markup); scenarios send `<script>` and `<b>` and read them back unchanged.
- **Permissions.** `profile.update` for the profile calls, `messages.send` for sending, replying and creating or cancelling a request, `accounts.manage` for connecting and disconnecting (the shell's launch points already used these; the spec says `accounts.view` for all of them), `accounts.view` for the two views. The bank refuses without them (`PERMISSION_DENIED`).
- **A failure path for every call**, with the words of the spec ("Nothing was changed.", "Nothing was sent.", "Nothing was connected."); a slow answer never says the action happened, and the text of a message, a request and a profile form stays in the form.
- **Connected accounts are read only.** A connected bank lives with the customer's linked banks (`finance.linked`), never among the accounts a payment can start from; `bank.accounts.list` and `bank.accounts.payFrom` do not list them, and the bank refuses to move money out of them. The bank asks for the agreement itself (`CONSENT_REQUIRED`), needs a connection that was started (`STATE_INVALID`), refuses a bank that is already connected or not answering and a choice of no account. The other bank's password never reaches BankWorkx: there is no field for it. Micro-deposit verification is not in the spec and is not built (no money is moved, so no amount is verified).

### Money safety, privacy and security, as built

- **Exact money.** The calculators work in minor units with integers and BigInt fractions (no floats): the loan payment is `P * num * A / (den * (A - B))` rounded half up, a deposit's interest is an integer sum. The bank's quote is the one that counts; a screen shows what the bank answered.
- **A code before an account is made or enrolled.** Open an account, track an application and register all need a one-time code (the sign-in's model: 482100, wrong 000000, expired 999999, 5 minutes, 3 resends, 3 wrong codes lock for 30 minutes). Registration reuses the sign-in's credentials: a hashed password (`secretHash`), the password rules, a trusted device.
- **Consent before submit**, asked by the bank (`CONSENT_REQUIRED`), not only by the screen.
- **Nothing sensitive is kept.** A draft keeps the answers except the ID number and the tax ID (a hash and a mask); photos and codes are never kept; after submit the application keeps the reference, product, stage and masks. `sandbox.public.inspect {contains}` proves that a string is nowhere in the bank's record. Tests look at the journeys' data and transcripts, the outbox and the log for the typed values; secure fields never reach a transcript. A secret is never echoed back (the confirmation shows the username and "Trusted", never the password).
- **What the person writes is data.** A message and a name are stored as written and drawn as text; scenarios send `<script>` and `<b>`.
- **Before sign-in, only the public adapters answer.** The signed-out allow-list (`PUBLIC_ADAPTERS`) is added deliberately, and a test checks that every other adapter still answers `NOT_SIGNED_IN`.
- **A failure path for every call** (unavailable, timeout, slow answers); typed values stay on the screen and nothing says it was done when it was not.

### How they differ from the spec, and why

The engine has no sliders, live redraw, maps, camera, per-field messages from the bank or link action, so:

- **Calculators.** The amount is a field with chips (not a slider) and the term a list. *Start application* goes to the sign-in (`apply-loan` and `term-deposit` need a customer) instead of opening the product.
- **Find a branch or ATM.** A list with details, no map and no directions (no link action); the distance is the sandbox's fixed figure for a made-up place, not a measured one; an hour of 24:00 is shown as the bank sends it.
- **Open an account.** The photo capture is simulated (no camera, nothing saved); no file upload; the ID number is asked again on resume, by design.
- **Contact us.** Chat and call show the hours; they do not open a chat or a dialer (no link action).
- **Landing.** Three actions beside Sign in (open an account, register, track) and four Explore rows, for web and phone. Not built: Products, Exchange rates, the legal pages, the welcome carousel and the splash. Apply for a loan, Term deposit and New message from a public screen go to the sign-in.
- **Where the spec's text and its criterion disagree**, the criterion is followed (for example 12 months is shown as "1 year").

### Money safety, privacy and security, as built

- **The bank decides.** A screen hides what a role may not do, and every call is refused again by the sandbox: `PERMISSION_DENIED` for a role without the permission or another `userId`, `WRONG_CONTEXT` from Personal, `ACCOUNT_NOT_PERMITTED` for an account whose transactions or export the person has no right to (Alex at Beta sees the balance of *Payroll* and nothing else of it; at Alpha he may not pay from *Reserve*). Forced calls are proved in the scenarios (`expectBankError`) and each rule has a mutant.
- **A code where money or the list of who may be paid changes.** Add a supplier always asks for a code. Scheduling or changing a payment asks from 25,000.00 in the company's currency (Euro and Pound amounts are converted at the sandbox's mid-market rate), never to cancel, and the code names the amount, the supplier and how often. Statements, templates, withdrawing and cancelling ask for none (the spec: nothing is paid and nothing can leave). Three wrong codes stop the request.
- **Maker-checker.** Nobody approves what they started (unchanged); a Maker can only withdraw his own payment (`NOT_YOUR_PAYMENT`), a released one cannot be withdrawn (`PAYMENT_RELEASED`), and a new supplier or a change to a schedule waits for someone else; a change clears earlier approvals.
- **Approval rules and limits are the bank's.** Two approvers above 50,000.00 USD (the review says so before the code), the person's limit per scheduled payment (250,000.00), the Standard speed's limit (25,000.00 for the first home market) for a schedule, the cooling-off of a new supplier as the spec says it (the line is shown; payments to it are not capped yet), the 20 templates and 20 schedules and the 10 waiting suppliers.
- **Consent.** The confirmation tick is required before a schedule, a change or a supplier request is sent (the spec has none; the money rules ask for it), and *Add anyway* before a name that is not a match.
- **Failure paths.** Every call has an `onError`: an unavailable bank shows the sheet "We couldn't reach the bank" with Try again, a slow answer to a question that changes nothing says "Nothing was changed", and a slow answer to a call that creates or changes something sends the person to check (Check Suppliers / Scheduled payments / Payments) so nothing is done twice. Nothing is created or changed when the call fails.
- **Personal data.** The audit trail names the action and the company's own names only ("Asked to add supplier Brightline Packaging", "Withdrew payment PAY-2040 of $18,900.00"); account numbers are shown only where the person needs them to receive money (the detail of an account, with `opt.details`) and a supplier's account is shown masked ("021000021 · ••4321", "DE44 •••• 4931"). No code, password or full number is in a transcript or a log.
- **Exact money.** The sandbox's company books keep whole currency units with the currency's own decimals (as they did); every new sum (the total, what is on hold, the available balance, the transactions of a statement) is made in the smallest unit and converted back, and a conversion rounds half up.

### How they differ from the spec, and why

The engine has no live redraw, no per-field messages from the bank, no clipboard, no list-and-pane on a wide screen and no skeletons, so:

- **The bank's checks come with Continue.** The accounts and the period of a statement, the supplier's name and bank details, the name of a template, the dates and the amount of a schedule are checked when Continue is pressed, and the bank's words are shown on the step they belong to (a banner, not a message under the field). The name check of a supplier is a screen of its own (*The name is close* with *Use*, *Wrong type of account* with *Switch to*, *The name doesn't match*) instead of a box that updates while the person types.
- **Business accounts.** The detail is under the table, not beside it; the period and the search are applied with a button (*7 days* … or *Search*); *Copy details* says "Account details copied" (no clipboard); the 25-row cap shows "n of m shown"; available is the ledger less the pending outgoing items and the payments waiting for approval (the Alpha Operating account is $480,000.00 ledger, $458,760.00 available).
- **Statements and reports.** *Reports* and *Statements* (the shell lists of generated files, `corp.statements.list` of the spec) are not built; the journey reads `corp.statements.list` for the schedules that exist and the default address only. `launch.reportType` is not read. The 24-month check is "to is after from plus 24 months".
- **Add a supplier.** Step 2 is checked and then the name is checked (two bank calls); the Autofill of sample values is not built; the first 24 hours cap (`opt.newCap`) is shown on the review and the receipt only, as the spec says; the supplier waits as `waiting_approval` and can be listed (`corp.suppliers.list` with `include: "all"`); there is no administrator approval in the app (the Admin journeys are slice C), a scenario approves one with `corp.sandbox.arrange`. Only the supplier's countries of the sandbox are offered (17), and a bank code is asked for Canada, India and Australia.
- **Payment templates.** The amount limit is "the person's limit" in dollars (250,000.00), tested on the dollar value; the template is shared by the company's Makers; *Use* hands the template to Pay a supplier as `launch.templateId`, which also carries the reference and the purpose (the spec says they are not carried yet).
- **Templates and Scheduled supplier payments.** A row opens a card with *Use* / *Delete* or *Change* / *Cancel* instead of buttons at the end of the row; the status is a chip column; *Paused* is not drawn (nothing sets it).
- **Schedule a supplier payment.** The dates are the calendar field (the bank refuses today, a weekend, a closed day and more than 12 months); "On a date" shows the dates the bank offers on a screen of its own after the first date; the confirmation tick is added; *Change* sets the first date again from the chosen next date and counts the payments from there; a change to a schedule or a new one sits as "awaiting" (the approval of a schedule by approvers is not built; the sandbox has no run engine, so no payment is started on its date); `reminder` is not read. **Where the spec disagrees with itself the rule is followed:** scenario T-3 of the spec schedules 60,000.00 to Harbour Packaging to show *Needs 2 approvals*, but the same spec limits a scheduled payment to the Standard speed (25,000.00 for the first home market), so the scenario uses Nordic Supplies AB (60,000.00 EUR, paid abroad, no Standard limit) and Harbour Packaging at 60,000.00 is refused as over the limit (T-4).
- **Withdraw a payment.** The tracker's *Pending* button of the spec is not needed (the pick step lists them); the reason and the note are stored by the bank with the withdrawal (`withdrawReason`), which the tracker's timeline shows.
- **Payment tracker.** *Settled* is a payment released on an earlier day (the sandbox has no settled state): PAY-1187 is Settled, a payment released today is *Released to bank*; filters by date, type or person, the search, the sort by column, the *Mine* toggle, *Save as template*, *Repeat* and *Repair rejected lines* on the detail, and the lines table of a bulk payment are not built; *View receipt* is the page's receipt (print or share), not a file.
