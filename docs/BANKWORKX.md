# BankWorkx: a second bank app on the same platform

BankWorkx is a money-management app (balance, spending, budgets, cards) built on the same journey engine as Meezan Digital. Its look follows the fintech design kit you supplied: a lavender canvas, a blue gradient balance card, cyan highlights, a mint action button, rounded cards, charts, and a bottom tab bar.

It shows that one codebase can carry several banks: the journeys, engine and Studio are shared, and each bank brings its own look, name, ids and sandbox customers.

## Run it

```bash
# 1. Studio (a second terminal), then load the BankWorkx journeys into it
cd apps/studio && pnpm dev
cd apps/studio && npx tsx scripts/seed-journey.ts all        # add-money, add-card, connect-account, create-budget

# 2. The app in a browser
pnpm bankworkx:web

# 3. Or on the iPhone Simulator / an Android emulator
pnpm ios:sim --brand bankworkx --install
pnpm android:apk --brand bankworkx --install
```

Without Studio the app falls back to the journeys bundled inside it, so the demo still works offline.

## Checked on

The web build, and the iOS Simulator (iPhone 17 Pro, iOS 26.5): sign-in, dashboard with the chart, the action sheet, a full *Add money* journey with a balance update, and dark mode. All four journeys ran on iOS (typed card number, hidden password, switches, tiles). The first BankWorkx iOS build took 1 min 27 s and rebuilds about 50 s. On an Android 14 emulator the app starts in under half a second and the dashboard renders fully (the 21.8 MB APK is `bankworkx-0.1.0-1-uat-arm64.apk`); on 2 November 2026 the Invest screens also ran there: the portfolio, a stock page, the watchlist star, and a *Sell investment* sale ($50 of a holding, with the position updating). The other journeys were not re-run on Android. A real iPhone has not been tried. To open BankWorkx on the emulator: `FINX_BRAND=bankworkx node apps/bank-app/scripts/android-emulator.mjs launch`.

### Launch values and opening one journey from another

**Launch values.** A journey can be opened with values at data paths that are there *before* its entry screen runs, so the entry (its `onEnter`, a branch screen, `navigation.rules`) can branch on them. Apps: `app.openJourney(slug, initial, launch)`; players: the `launch` prop (renderer-core: `launch` option of `JourneyRunner` and `JourneyController`). Existing `initial` answers are unchanged: they are still filled in *after* the first screen opens. Without launch values nothing changes. By convention the journey reads them at `launch.*` (for example `launch.type`, `launch.operatorId`), copies what it wants into its own data on the entry screen and, where it should be used once, clears it (Mobile top-up). Scenarios take a `launch` object (and the simulator a `launch` option).

**Opening another journey.** `{ "type": "navigate", "toJourney": "personal-transfer", "with": { "launch.type": "international", "pt.note": "{{t.note}}" } }`. The values are read from the calling journey's data at that moment (a `with` value that is a whole `{{template}}` keeps its type) and passed as the other journey's launch values; the bank's options (`opt.*`) go along, because they belong to the bank. A navigation rule of the screen that matches wins over `toJourney`, as it does over `to`. The runner raises the request (`openJourney` option, `onOpenJourney` on the controller and the players); the app opens the target by slug the way `openJourney` does, including a copy made for the bank (`personal-transfer-acme`): `BankApp.openChained` in the apps, a route change in the web app. A target that cannot be loaded closes the calling journey with the notice "That journey is not available right now." In the Studio preview, where only the journey being edited is loaded, nothing opens: the screen says "This step opens another journey, which is not loaded here." and the person stays.

**`returnTo`.** Not built, and it does nothing: the calling journey is *replaced* by the target, and nothing comes back to it when the target ends (the person goes back to the app). It stays in the schema, reserved, so that a journey that sets it keeps working. It needs the calling journey's state to be kept and restored; that is the follow-up.

**Lint.** `with` values are checked like other templates (an unknown data path is a lint issue). A `toJourney` that is not a journey of the catalog or of BankWorkx or CAB is a *warning* (the advice of `finx_lint_journey` / `finx_save_journey_draft`, code `unknown_journey`), not a blocking issue, since a bank may add its own journeys. The expression `get(map, key)` reads an entry whose key is data (for example the operator the journey was launched with in `ctx.carriers`).

**Where it is used.** *To a BankWorkx customer* and *Abroad* open Send money with `launch.type` (their 20 screens are no longer copied; their scenarios follow the chain in the simulator, `expectOpens` asserts what was opened, so every rule is proved where it lives; Send money gained AC-14 for being opened with a type). *Mobile top-up* takes `launch.operatorId`. The simulator follows a chain to journeys it is given (`journeys`, default: the BankWorkx journeys) and otherwise records "opens journey X with values Y".

They carry `apps: ["bankworkx"]`, so the Meezan app never shows them. A journey with no `apps` belongs to Meezan.

## Invest

Nine made-up stocks and funds (Lumen Robotics, Apex Cloud, Harbor Energy, Orchard Foods, Summit Health, Meridian Bank, Global Index Fund, Green Future Fund, Treasury Bond Fund). Their prices and charts are fixed, so the same symbol always draws the same chart and ends at today's price. Alex starts with four holdings and three watchlist entries; Sam (the new customer) starts with none and sees *Start investing*.

- **A stock or fund page** has the price and day change, a chart with 1D / 1W / 1M / 1Y (drag to read a point), your position (value, shares, average cost, return), key numbers, a short description, a star to add it to the watchlist, and *Buy*.
- **Selling** is the *Sell investment* journey, and the *Sell* button shows on the page of anything you own.
- **Buying** is the *Invest* journey: it takes money from the chosen account, buys part of a share at today's price, and adds to the holding at a new average cost. The portfolio, the dashboard card and the transaction list update.
- Sandbox adapters: `bank.invest.instruments`, `bank.invest.holdings`, `bank.invest.buy`, `bank.invest.sell`, `bank.invest.watch`.
- All of it is sandbox data and the screens say it is not investment advice.

## New building blocks

These are available to every journey, in Studio's block picker and in the AI tools:

| Block / option | Use |
|---|---|
| `amountInput.quickAmounts` | One-tap amount chips |
| `select` with `variant: "tiles"` and `choices` | Big option cards with an icon and a line of help (banks, account types, categories) |

| `toggle` | An on/off switch for a yes-or-no choice |

Charts, the gradient card, the donut, icons and pills are shared widgets in `packages/renderer-native/src/widgets.tsx`.

## How a bank is defined

A bank is a **project**: see [PROJECTS.md](PROJECTS.md). In short, `packages/ui-kit/src/brands.json` holds each bank's name, ids, look ("preset"), accent colour and currency; the design system turns that into a full light and dark theme, and Studio can add new ones. The sandbox customers are in `packages/mock-bank-api`, tagged by look. Banks with a Personal and a Business side can theme each apart (BankWorkx has Aurora and Graphite); see [WORKSPACE-THEMES.md](WORKSPACE-THEMES.md). Build with `--brand <id>`. Icons come from `scripts/generate-brand-assets.py` (the build makes them if missing).
